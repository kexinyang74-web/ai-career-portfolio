> 第 10 周交得出项目二评测。这周管 **多步骤任务谁来调工具**。今天只搞概念，**不调 Chat API、不写 LangGraph、不建项目三仓库**。Day 70 休息跳过。

对照将做的项目三：热点追踪选题日报。抓热点、按赛道筛、写成日报——这三件是 **工具**；模型只负责决定「下一步调哪个」。今天先能画出四步，并分清它和纯 Chat、RAG 的差别。

## 三条路（先记谁动手）

| | 纯 Chat（项目一） | RAG（项目二） | Function Calling（这周） |
|---|---|---|---|
| 资料从哪来 | 模型参数里的「常识」 | **你**先检索，片段塞进本轮 `user` | **你**按模型点名去跑函数 |
| 模型输出 | `content` 给用户看 | 仍是 `content`（被资料约束） | 可能是 `content`，也可能是 `tool_calls` |
| 下一步谁决定 | 没有下一步 | 你在提问前就检索完了 | 模型看任务再选工具；你执行后再问它 |

Agent 不是新模型。和 RAG 一样，约束在流水线：**它不能真的上网或写文件，只能发出「请调用」的 JSON**。

## 四个步骤

```text
你：messages + tools（schema）
        ▼
模型：content（结束） 或  tool_calls（名字 + 参数）
        ▼
你：用 Python 执行对应函数（查表、算数、写文件……）
        ▼
你：把 assistant（带 tool_calls）和 role=tool 的结果追加进 messages，再 POST
        ▲________________ 直到出现给用户的 content，或步数用尽
```

1. **schema**：每个工具的 `name`、`description`、`parameters`（JSON Schema）。描述写糊了，它就会选错工具或乱填参数。
2. **tool_calls**：模型这一轮的「行动意图」，不是已经发生的事实。
3. **你执行**：真正的副作用在你这边。函数报错也要变成一段文字结果交回去，不要假装成功。
4. **回传**：下一次请求必须带上「它说要调什么」和「你跑出来的观察」，否则它会以为工具从没发生过。

ReAct 只是给这圈起的名字：Thought（还要不要调）→ Action（tool_calls）→ Observation（tool 结果）。明天才写代码。
