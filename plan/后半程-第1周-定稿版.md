# 后半程第 1 周计划（2026-10-01 至 2026-10-07）

> 目的：先确认本人能独立写到哪里，并把现有 FastAPI 项目的请求链路讲清。任务说明看本文件；进度打勾见 [[后半程-第1周-进度追踪]]。

## 本周不做

- 不让 AI 生成完整函数或项目骨架。
- 不开 PostgreSQL、Docker、LangGraph、Dify。
- 不继续 Day 74 的三个假工具。
- 不追着补旧周欠账。

## 每日安排

| 日期 | 主任务 | 当天产出 |
|---|---|---|
| 10/1 | 基线诊断：在现有 `media-topic-assistant` 中找出一个请求从路由到返回的路径 | 手画/手写链路；指出文件和函数，不要求改代码 |
| 10/2 | 从空文件独立写函数与模块：输入列表，清洗并汇总内容素材 | 本人代码；至少包含类型注解和两个函数 |
| 10/3 | 为昨天代码加文件读写和异常处理 | 正常文件、缺失文件、坏数据三种运行结果 |
| 10/4 | 重新读现有 FastAPI 路由，用自己的话逐段解释 | 路由、参数模型、业务函数、数据库、返回值五个位置 |
| 10/5 | 遮盖重写一个不超过 20 行的现有函数 | 原版与本人重写版 diff；记录一个没想起来的点 |
| 10/6 | 故意改坏一处并先预测，再用报错或日志定位 | 预测、实际报错、定位层级、修复结果 |
| 10/7 | 本周验收与 5 题自测 | 本人作答；AI 后续只批改，不代答 |

投递并行：继续核实简历事实并投 A 类岗位；本周投递不要求等技术验收完成。

## 检查点

- [ ] 能独立写函数、模块、类型注解、文件读写和异常处理。
- [ ] 能指出一个 FastAPI 请求的路由、参数、业务函数、数据库和返回值。
- [ ] 能根据报错判断至少是接口层、业务层还是数据层。
- [ ] 能展示一次遮盖重写和一次故意改坏的证据。
- [ ] 日志三栏由本人填写，5 道自测由本人作答。

## 本周自测 5 题（不含答案）

1. 一个请求进入 FastAPI 后，最先匹配的代码通常是什么？
2. Pydantic 模型在接口里解决什么问题？如果没有它，坏输入可能在哪里出错？
3. 路由函数和业务函数为什么不应该全写在一起？
4. `try/except` 应该包住哪一小段？为什么不能把整个程序都包住后只打印「出错了」？
5. 如果接口返回 500，你准备按什么顺序判断是接口、业务、数据库还是外部模型的问题？
