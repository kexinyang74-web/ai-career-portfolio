## 一个我能讲清楚的原理（本人填写）

（例如：venv 是干嘛的？为什么要用虚拟环境？requirements.txt 怎么用？.env 为什么不能进 git？）
1. venv 就是虚拟环境，当你的命令前面出现 `(.venv)` 说明你现在已经在虚拟环境中了
2. 相当于购物清单，让别人能清楚看到有什么依赖，可以精准对照。使用方法是 `pip install -r requirements.txt`。用这条命令可以按照清单内容一键安装
3. 因为里面包含密钥，会造成密钥泄露，这是会流失真金白银的。

> **批注（Claude）**：
> - 原理 1 ✅ 准确。补充：`(.venv)` 是激活成功的标志；更本质的验证是 01_where_am_i.py 打印的 `sys.executable` 路径（带 .venv 才是抽屉里，不带就是全局）
> - 原理 2 ✅ 比喻很好。补上"出口"：清单还有导出环节——`pip freeze > requirements.txt`。**freeze 管导出、install -r 管安装**，一出一进才是闭环（今天你亲手跑了两头）
> - 原理 3 ✅ 说对了。"流失真金白银"很形象：密钥泄露可能被人刷掉大额 API 费用。所以配套动作是 .env 进 .gitignore + .env.example 模板进 git

## 遇到的问题（本人填写）

一开始把 venv 建在了仓库根目录，因为新开的终端默认停在根目录、没先 cd。cd 到目标路径（day22）再建环境就好了。

> **批注（Claude）**：修正一处表述——venv 是建在了**仓库根目录**（学习安排），不是"全局环境"。这两个概念要分清：
> - **全局环境**：`D:\proflim\python.exe` 那个所有项目共用的 Python（requests 2.34.2 在里面）
> - **根目录 vs day22**：只是"建的位置不对"，环境本身还是局部的
> 你说的现象很敏锐（新终端目录会重置），这也是今天最重要的坑之一：**相对路径命令的基准 = 终端当前目录**，跟脚本位置无关。
