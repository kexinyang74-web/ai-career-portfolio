```python
@app.patch("/api/topics/{tid}")
def patch_topic(tid: str, body: TopicPatch):
    with writing():
        topic = topic_or_404(tid)
        updates = body.model_dump(exclude_none=True)
        if updates.get("favorite") and not topic["favorite"]:

        topic.update(updates)
        return db.save_topic(topic)
```

## 第 1 题

**为什么必须先确认 `tid` 对应的选题存在，再对选题字典做修改？如果顺序反过来，可能出现什么结果？**

你的答案：
> 顺序反过来的话，如果tid选题一开始不存在，系统不会第一时间报错。

判定：⚠️ 半对。只答了"反过来"的后果，而且说得很含糊；主问题（为什么必须先查）没答。

批改：
- 你抓对了一半：先查存在性 = **fail fast（快速失败）**，一发现不存在就立刻 `404`，后面所有修改步骤一步都不执行，**不会留下任何副作用**。`topic_or_404` 抛异常时，`topic.update(updates)` 根本没机会跑。
- "不会第一时间报错"这个后果讲得太轻。顺序反过来的真实结果：
  - `topic_or_404` 返回 `None`，接着对它 `topic.update(...)` 会直接 `AttributeError` 崩掉（不是干净的业务错误）；
  - 就算你把判断挪到只在校验里，最后 `db.save_topic` 的 `UPDATE ... WHERE id=?` 也匹配不到任何行——**静默地什么都没改**，接口却可能回个"成功"，这类 bug 最难查。
- 一句话记法：**校验在前 = 有错早报且不留痕；校验在后 = 要么崩得难看，要么悄悄失败。**

## 第 2 题

**请求体模型中有四个可选字段。怎样只取出客户端这次真正提供、并且不是 `None` 的字段？这样做保护了什么？**

你的答案：
> 通过字典键和值，单独列出想取的键。
> 保护了什么：保护了修改范围，如果不筛选，可能会把所有可选字段全都修改

判定：⚠️。第二问方向对，第一问没答到点上——没说出准确方法。

批改：
- 你说的是"思路"，但代码里靠的是 `body.model_dump(exclude_none=True)` 这一个动作：它把请求体模型转成字典，并**丢掉所有值为 `None` 的字段**，只留下客户端真正给了值的。不是手动"单独列出想取的键"。
- 第二问基本对：不筛选的话，没传的字段会带着 `None` 一起 `update` 进去，把原有值**抹成空**，也就是"改大了修改范围"。这点你说对了。
- 补一个精确度：这里用的是 `exclude_none`（排掉值是 None 的），不是 `exclude_unset`（排掉没传的）。两者在"客户端显式传了 `null`"时结果不同——有兴趣明天可以抠一下这个差别。

## 第 3 题

**当客户端把 `favorite` 从假改成真时，为什么代码还要联动修改 `status`？这属于输入校验、业务规则还是数据库操作？**

你的答案：
> 因为修改status才会修改数据库，
> 不知道

判定：⚠️ 偏错。第一句是错的，第二问等于没答。

批改：
- 先纠错：**改 `status` 不改数据库。** `topic["status"] = "待创作"` 只动了**内存里的字典**，真正写进 SQLite 的是最后那句 `db.save_topic(topic)`。你把"改字段"和"存数据库"混成一件事了——这正是第 4 题要你分清的那条线。
- 正确答案：这属于**业务规则**。业务含义是——"一个之前没被收藏的选题，一旦被收藏，就重新拉回 `待创作` 队列"。这是产品/业务定下来的联动逻辑，跟"格式对不对"（输入校验）、"怎么落库"（数据库操作）都不是一回事。`if updates.get("favorite") and not topic["favorite"]` 里的 `not topic["favorite"]` 就是在防"本来已收藏还重置状态"。

## 第 4 题

**"把 `updates` 合并进 `topic`"和"调用保存方法"分别改变了哪里？为什么前者不能代替后者？**

你的答案：
> 两者都是改变topic,前者是把updates的值合并到topic中。调用保存方法也是将topic和数据库段进行保存。
> 前者不会接触到数据库端

判定：✅。核心抓对了。

批改：
- 关键结论你说对了：`topic.update(updates)` 只改**内存中的字典**，`db.save_topic(topic)` 才把字典**写进 SQLite**（`UPDATE topics SET data=?`）。两者一个改内存、一个改磁盘/数据库，前者不能代替后者，因为**内存里的改动不落库，进程一结束就没了**。
- 小修：`db.save_topic` 不是"把 topic 和数据库段进行保存"，而是**把 topic 序列化后写回它在数据库里的那一行**；它自己还会 `return topic`（这点在第 5 题很关键）。
- 你这题是五题里答得最扎实的一道。

## 第 5 题

**如果函数成功保存了数据但漏写 `return`，数据库和浏览器分别会看到什么结果？**

你的答案：
> 对应的函数仍会运行，但是不会立刻结束。体现在数据库端则是不会收到修改后的数据，浏览器也不会有修改后的数据。

判定：⚠️。前半对，**数据库那半说反了**。

批改：
- "函数仍会运行"对；"不会立刻结束"这个说法不准——漏 `return` 不会让函数卡住或延迟，函数照样正常跑完，只是**返回 `None`**。
- 关键错误：**数据库会收到并保存修改。** 保存动作是 `db.save_topic(topic)` 那句，它在 `return` 之前就已经执行完了，落库和有没有 `return` 无关。你说"数据库收不到修改后的数据"是反的。
- 浏览器的结果：FastAPI 把返回值 `None` 序列化成 **`null`**，所以浏览器收到的是 `200` + 一个 `null`（或前端拿不到期望的 topic 对象），**不是**"没有数据更新"这么简单——数据其实更新了，只是前端看到的是空返回值。这类 bug 很坑：库里对了、界面像没生效。

## 收口两问 · 批改

### 第 1 问

你的答案：
> 会让数据库接收数据并保存修改数据

判定：⚠️ 答对一半。提示说了"两件事"，你只捡了数据库那件。

批改：`db.save_topic(topic)` 里其实做了**两件事**——
1. **写库**：`db.execute("UPDATE topics SET data=? WHERE id=?")`，把序列化后的 topic 写回那一行（你这半答对了）；
2. **返回**：函数结尾是 `return topic`，把**内存里那份 topic** 交回去。

而 `patch_topic` 写的是 `return db.save_topic(topic)`——**外层 `return` 拿到的，正是内层 `return` 交回的那个 topic**。这就把第 5 题补全了：漏掉外层 `return` 时，写库照做（第一件事不受影响），但没人把这个 topic 交给 FastAPI，浏览器就只拿到 `null`。

一句话：**保存 = 写库 + 交回对象，你之前只记住了写库那一半。**

### 第 2 问

你的答案：
> 不知道，

判定：⚠️ 诚实标记，有效。这里给结论，不留作业。

批改：会出问题，而且问题不小。核心原因是**接口不只有前端一个入口**——浏览器只是调用者之一，别人可以直接 `PATCH /api/topics/{tid}`，绕过前端页面。所以：

- 写成**前端逻辑**：只要不走你这个页面（直接打接口、以后加小程序/其他客户端、脚本批量改），"收藏→重置状态"就失效，各个入口行为还不一致；
- 写成**后端逻辑**：这条规则挂在服务端函数里，**谁调都生效**，前端换了、加了新端，规则都不用重写。

这就叫"业务规则要有**单一权威来源**"。一条规则如果多个入口都要用，就必须沉到后端最里层，而不是指望每个前端各自记得做一遍——放到前端，等于同一条规则散落多处，迟早漏一处。

（补一句诚实的：也不是所有联动都非放后端不可。判断标准是"这条规则是不是**任何入口都必须成立**"。是 → 后端；只是某个页面自己的显示小心思 → 前端也凑合。本题这种改数据状态的联动，属于前者。）
