# Day 6｜故意改坏一处，先预测再用报错定位

日期：2026-10-07

## 今天的目标

在现有项目里主动制造一个 bug：先写下你预测会发生什么，再运行、看报错或日志，判断故障出在接口层、业务层还是数据层，最后修复，让项目回到干净状态。

## 为什么练这个

真实开发里代码几乎不会一次就写对。比"一次写对"更常用的技能是：**看到报错，能判断是哪一层坏了**。今天把这条反应练成条件反射。这也是本周检查点里的一条。

## 三层故障的"长相"（先记长相，别背定义）

- **接口层**（路由登记、路径、参数校验）：一般直接给客户端 `4xx`——`422`（输入不符合要求）、`404`（路径/资源不存在）。特点是**在业务代码跑起来之前就被拦下**。
- **业务层**（路由函数里的判断和赋值）：Python 异常从函数里冒出来（`AttributeError`、`KeyError`、`TypeError`…）→ `500`；或者**根本不报错，但结果悄悄错了**（字段被覆盖、状态不对）。
- **数据层**（`store.py` 里的 SQL）：写不进、`UPDATE` 影响 0 行、重启后数据没了；或 sqlite 自己报错。
- **外部模型层**：provider 超时或返回格式不合格 → `502` / `ProviderError`。（今天先不碰这层，但记住它存在。）

### 第 1 步：三个"改坏点"，三选一（有余力就都做）

每个改坏点**只改一处**，其余一行都别动。先别急着改，先做第 2 步的预测。

- **改坏点 A（接口 / 参数模型）**：把 `def patch_topic(tid: str, body: TopicPatch)` 里的 `body: TopicPatch` 改成 `body: dict`，其他不动。
- **改坏点 B（业务）**：把 `updates = body.model_dump(exclude_none=True)` 里的 `exclude_none=True` 改成 `exclude_none=False`。
- **改坏点 C（数据）**：把 `return db.save_topic(topic)` 改成 `return topic`（只改了内存，不落库）。



### 第 2 步：先预测（不改代码，写在下面）

针对你选的改坏点，先回答三问：

1. 哪一层会先"炸"？（接口 / 业务 / 数据）业务层
2. 客户端看到什么？`422`、`404`、`500`，还是"表面成功但数据不对"？422
3. 哪个测试会变红？你猜它红在哪一行断言？



### 第 3 步：改一处，保存

只改那一行。改之前先看清自己把什么改成了什么。

### 第 4 步：运行并保留原文

```powershell
.\.venv\Scripts\python.exe -m pytest tests/test_app.py -q
```

把失败输出的**关键几行原文**抄进记录表——不要只写"报错了"。

### 第 5 步：定位层级

对照你的预测给出结论：这次故障属于哪一层？证据是哪一行？

- `4xx` 且业务代码没跑 → 多半**接口层**；
- Python 异常冒出来 → **业务层**（要看异常类型，别只看"500"三个字）；
- 没报错但数据不对、或重启后没了 → **数据层**，或业务层写错了位置。



### 第 6 步：修复并复原

改回原样，或用 `git checkout -- ...app.py` 还原。再跑一次测试，确认回到基线的通过数。
