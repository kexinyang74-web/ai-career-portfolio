## 第 1 题

**一个请求进入 FastAPI 后，最先匹配的代码通常是什么？**

你的答案：
> `@app.patch(api/patch/{tid})`

判定：⚠️ 方向沾边，没答到点上。

批改：
- 题目问的是"最先匹配的**代码**"。FastAPI 收到请求后，第一步是**拿 URL 路径 + HTTP 方法，去路由表里找哪条路由能对上**。这张"路由表"就是你用 `@app.patch("/api/topics/{tid}")` 这类装饰器登记进去的。
- 所以"最先匹配的"就是**路由本身（方法 + 路径）**；匹配上了，才轮到它绑定的处理函数 `patch_topic()` 运行。
- 你写的 `@app.patch(...)` **方向没错**——装饰器正是登记路由的地方。但两个问题：
  1. 你把它当成"某一条具体路由"举例了，题目要的是**通用**的一句话；
  2. 路径写错：不是 `api/patch/{tid}`，是 `/api/topics/{tid}`（少了开头 `/`，`topics` 不是 `patch`）。
- 一句话答案：**最先匹配的是路由（HTTP 方法 + 路径），也就是装饰器登记的那条；匹配上了才调用处理函数。**

## 第 2 题

**Pydantic 模型在接口里解决什么问题？如果没有它，坏输入可能在哪里出错？**

你的答案：
> 不知道

判定：⚠️ 没答。

批改：
- **解决什么**：入口的**校验 + 解析**。请求体 JSON 一进来，FastAPI 先拿模型（`TopicPatch`）检查——字段类型对不对、值合不合法；不合格**直接 `422`，处理函数一行都不跑**；合格才帮你把 JSON 转成一个好用的对象（`body`）。
- **没有它会怎样**：坏输入会**漏进函数体**，然后在**任何一步**才炸——
  - 可能在业务逻辑里抛 `TypeError` / `KeyError`（→ 500）；
  - 也可能不报错，但数据**悄悄写错**。
  校验点从"门口"退到了"屋里"，定位难得多。
- 这就是你 Day 6 改坏点 A 的现场：`body: TopicPatch` 改成 `dict`，校验没了，坏输入直接进函数，报错位置从接口层挪到了业务层。

## 第 3 题

**路由函数和业务函数为什么不应该全写在一起？**

你的答案：
> 不知道

判定：⚠️ 没答。

批改：核心是**职责分离**，三个"才有"：
1. **才可测**：业务逻辑单独成函数，才能不启动服务器、直接传数据测它（像 `save_topic`、`clean_money`）。全塞进路由里，就只能靠发 HTTP 请求测，又慢又难。
2. **才可复用**：同一段业务逻辑可能被多个接口调用；嵌在某个路由里就复用不了。
3. **才可定位**：路由只管"接请求、返回响应"，业务只管"怎么算"，数据库只管"怎么存"。出错时你知道该去哪一层找。
- 一句话：**路由是"接待台"，业务是"干活的人"，数据库是"仓库"。全挤进一个函数，测不了、复用不了、出错也找不到。**

## 第 4 题

**`try/except` 应该包住哪一小段？为什么不能把整个程序都包住后只打印「出错了」？**

你的答案：
> 不知道，这个问题很怪，你没说要判断哪一层的错误，
> 不把整个程序都包住是因为不好定位错误原因。范围太大。

判定：⚠️ 半对。第二问方向答对。

批改：
- 先说"问题怪"：这题**不是**问判断哪一层，是问 **`try/except` 该圈多大范围**。跟分层是两码事，你把它读成分层题了。
- **第一问（包住哪一小段）**：只包住**你预料到会出事、并且知道怎么处理**的那几行。比如读文件就只包 `open()` / `json.load()` 那几行——出 `FileNotFoundError` / `JSONDecodeError`，你才知道怎么接。**不要顺手段全圈进去。**
- **第二问（为什么不能全包）**：你答"**不好定位错误原因，范围太大**"——✅ **对！** 补完整：
  1. 真正的错误**类型和行号**被吞掉，你只知道"出错了"，不知道"哪儿、什么错"；
  2. 没法对**不同的错做不同的处理**（文件没找到 → 提示路径；JSON 坏了 → 提示格式）；
  3. 错误被掩盖后程序还继续跑，可能把数据改坏。
- 一句话：**`try` 的范围要"刚好包住会出事、且你会处理的那几行"；包太大 = 把报警器关掉。**

## 第 5 题

**如果接口返回 500，你准备按什么顺序判断是接口、业务、数据库还是外部模型的问题？**

你的答案：
> 不知道

判定：⚠️ 没答。

批改：一条从外到内的排查顺序：
1. **先看报错原文 / traceback**——栈顶那一行是哪个文件、哪个函数？它直接指出"崩在哪一层"。
2. **接口层**？`422`（不是 500）= 参数校验；`500` 且发生在**处理函数第一行之前** = 参数/路由问题。
3. **业务层**？traceback 指着路由函数体内的某行（如 `app.py:204` 的 `AttributeError`）= 业务层。看异常**类型**（`KeyError` / `AttributeError` / `TypeError`）。
4. **数据层**？traceback 指向 `store.py` 的 SQL，或"写没写进去、影响 0 行" = 数据层。
5. **外部模型层**？traceback 到 provider 调用，或返回 `502` / `ProviderError` = 外部模型层。
- 核心方法：**顺着 traceback 的栈，看它停在哪个"工位"**；状态码只作辅证。**不是靠猜。**
